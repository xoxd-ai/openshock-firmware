# Softproxy cap enforcement (xoxd-ai fork)

This fork of `OpenShock/Firmware` starts from tag `1.5.2` (commit `5546c13eb745e4fb2b4ca7b0f4160de8b261872c`). It adds one change: the hub checks every shock and vibrate command against operator-set caps before the radio sends it. Softproxy's alarm service checks the same caps first (Softproxy ADR-0008 decision 6, `Device.dhall` server check 3). The hub check is the second line. A step over the intensity, pulse, per-stage or gap caps cannot reach the shocker even when the server sends it. The hourly and daily caps hold across a warm restart, and a power cycle that loses RTC memory costs a full cold boot hold (see Fail closed). To keep the gateway from removing the check, the fork also refuses over-the-air installs and ignores the gateway restart trigger, and it refuses shock and vibrate from the gateway, so only the local serial port actuates (see Remote paths). The captive portal's local socket refuses the E-Stop, Wi-Fi and account-link commands (SP-46, see Local socket). The hub refuses shock and vibrate unless a live E-Stop stands behind them, a cap rises only while a button press holds the E-Stop engaged, and a cold boot starts engaged (SP-113, SP-156, SP-158, see Kill path). The E-Stop is a latching mushroom with a normally closed contact, so a cut cable or an unwired pin reads as stop (R-SOFTPROXY-ESTOP-NC). Each cap or E-Stop refusal reaches the hub log and the gateway heartbeat (see Refusal report). Linear: TIN-7545.

## What the hub enforces

| Cap | Hub rule | Refusal |
| --- | --- | --- |
| `maxIntensityPct` | command intensity at most this, and at most 100 | `over-intensity` |
| `maxPulseMs` | command duration at most this | `over-pulse-ms` |
| `maxPulsesPerStage` | commands in one stage at most this | `over-pulses` |
| `minGapSec` | a new stage starts at least this long after the previous stage started | `gap` |
| `maxPerHour` | stage starts in any 60 minutes at most this | `hourly` |
| `maxPerDay` | stage starts in any 24 hours at most this | `daily` |
| `maxPulsesPerStage` times (`maxPulseMs` plus 73) | output time in one run at most this, each command counted with one radio frame (review H1, N2) | `over-on-time` |

Shock and vibrate have separate caps and separate counters. Stop, Sound and Light carry no cap. The keep-alive ping (vibrate at intensity 0) goes straight to the radio and is not counted.

A stage is one Softproxy request. A command starts a new stage unless `stageJoinMs` is above 0 and the command starts within `stageJoinMs` after the previous pulse of the open stage ends. `stageJoinMs` is hub-only and defaults to 0, so every command is its own stage and the gap applies between pulses.

The radio overwrites a shocker's running sequence with each new command for it, so commands that abut or overlap join into one unbroken output, whatever the stages (review H1, TIN-7545 `6fb2f27f`). The hub bounds that output per channel. A run is the channel's output from a start until it stays off for 300 milliseconds, the RF task's terminator time, after which the task has sent the stop frame for its full length and dropped the sequence. A short gap inside a run, under 300 milliseconds, adds no output time and does not end the run.

The RF task sends whole radio frames and starts one whenever a command's end still lies ahead, so a command can stay on the air up to one frame past its end (review N2). Each admitted shock or vibrate command above 0 ms therefore counts as output from its arrival for its duration plus one frame, and time where two commands overlap counts once. The frame is `kMaxRadioFrameMs` in `include/softproxy/CapLimiter.h`, 73 ms. It bounds the frame of every model the fork encodes: each item of a model's frame at the longest value any id, type and intensity gives it, summed, at the RF task's 1 microsecond tick. The Petrainer's bound is the largest, 72.2 ms, and its longest real frame is 69.2 ms (`src/radio/rmt/PetrainerEncoder.cpp`). The D80's 56.3 ms is the next largest. The command path host test rebuilds the bound from all five encoders and the tick, and fails if the constant drifts. A 0 ms command sends only the stop frame and counts nothing. A command that would take the run's counted time above one full stage counted the same way, `maxPulsesPerStage` times (`maxPulseMs` plus 73), refuses as `over-on-time`. The run ends 300 milliseconds after its last counted end, so the break on the air starts after the last frame.

What that leaves reachable, for `P` = `maxPulseMs` and `N` = `maxPulsesPerStage`:

| Quantity | Bound |
| --- | --- |
| Output on the air in one run, per shocker, any `stageJoinMs` | `N * (P + 73)` ms. Before review N2 a sender whose 1 ms commands landed at each frame start could hold it far longer with `stageJoinMs` above 0 |
| Commanded output in one run | `N * P + (N - 1) * 73` ms. A command may fill the frame that counts after an earlier one, so commanded time can pass `N * P` by up to one frame per earlier pulse, while the air stays within the row above |
| Break between runs on the air | at least 300 ms after the last frame, less any delay of the RF task between its end check and the frame that follows it (I) |
| A full stage | passes: `N` pulses of `P` count at most `N * (P + 73)`, which is the ceiling, whatever their spacing |

A pulse now counts as its length plus one frame. A stage whose pulses fit the caps still never reaches the bound by itself. The bound refuses a stage that would continue the previous stage's output with less than 300 milliseconds between them, when the joined output would pass one full stage. Since the counted end lies one frame past the commanded end, two stages join a run when the next starts less than 373 ms after the previous stage's last pulse ends. With `stageJoinMs` at 0 and `maxPulsesPerStage` at 1, stages at the minimum gap all pass only while `maxPulseMs + 373 <= minGapSec * 1000`. Above that, every second stage at the minimum gap refuses as `over-on-time`. Pacing that should never meet `over-on-time` starts each stage at least 373 ms after the previous stage's last pulse ends.

The run is kept per channel and not per shocker, so output to two shockers on one channel counts as one run, which can only refuse sooner per shocker. Each shocker stays within the bound, but two receivers on one channel commanded together each get the counted time, so their sum is twice it (review N4).

## Fail closed

- The fork ships no cap value. Every cap defaults to 0, and a channel with any cap at 0 refuses every command (Softproxy SP-9). Caps that are incoherent (intensity above 100, hourly above daily, `minGapSec * maxPerHour` above 3600, `maxPulseMs` above `minGapSec * 1000`) also refuse, as Softproxy `capsCoherent` does for the first three. The pulse rule is the hub's alone until Softproxy adds it: a pulse longer than the gap let stages started every `minGapSec` join into one output (review H1). A stored record that breaks it loads as 0, and `safetycaps shock` or `safetycaps vibrate` refuses it.
- A missing, unreadable or unknown stored record loads as all 0.
- The counters and the hub clock live in RTC no-init memory, sealed with a checksum after every shock or vibrate command the gate checks. A warm restart (software reset, panic or watchdog) keeps that memory, so the hub restores the counters, the output run and the clock where they were last sealed. The retained layout is version 2 since the output run joined it, so the first boot of this image after a version 1 image reads as a cold boot of the counters and holds. The downtime counts as not passed, so the clock never runs ahead of real time, which can only refuse sooner.
- A cold boot starts with the E-Stop engaged, and every command refuses until the clear (SP-158, SP-174, see Kill path). A cold boot is any reset outside the warm list there, such as a power loss, a brownout or an EN reset. One that loses RTC memory also fails the checksum. The counters then start empty and the clock starts at 0, so each channel refuses until the clock reaches the longest of `minGapSec`, 3600 s divided by `maxPerHour` and 86400 s divided by `maxPerDay`, rounded up (`boot-hold`). One that keeps RTC memory restores the counters and the clock, as a warm restart does, which can only refuse sooner, and it costs no hold. A hub that runs between power cycles can still exceed `maxPerDay` across them, so Softproxy's server counters stay the authority for the daily limit.
- The window counters use fixed buckets (1 minute for the hour, 15 minutes for the day). They can overstate a count by up to one bucket, which refuses sooner, and never understate it.

## Remote paths

Upstream lets the gateway replace the firmware and reboot the hub. Either would undo the hub check: an upstream image carries no caps, and a reboot used to empty the counters. Upstream also lets a linked gateway send shock and vibrate, which pass the hub caps and the E-Stop but none of Softproxy's server checks 4 to 8 (review H3). `include/softproxy/Lockout.h` closes all three, whatever the stored config says:

| Path | Upstream 1.5.2 | This fork |
| --- | --- | --- |
| Gateway `OtaUpdateRequest` | queues an install of any version from the CDN | `TryStartFirmwareUpdate` refuses |
| OTA check on startup or on a timer, a changed CDN domain | installs the found version | the OTA task stops before any download |
| Gateway `Trigger` `Restart` | `esp_restart()` | ignored and logged |
| Gateway `ShockerCommandList` Shock or Vibrate | sends within the caps | refused before `HandleCommand` and logged (`Refusing gateway <type>`), at compile time by `kAllowGatewayActuation = false`. The refusal does not count in the refusal report, which counts Softproxy's own steps. A gateway Stop and Sound still pass, and the gateway `Trigger` `EmergencyStop` still engages the E-Stop |
| Gateway `Trigger` `CaptivePortalEnable` | holds the portal open while the gateway is connected | ignored and logged (SP-46). `CaptivePortal::SetAlwaysEnabled(true)` also refuses, whatever the caller |
| Serial flash, serial `restart` | allowed | allowed, both need the local serial port |

## Local socket

The captive portal opens an access point with no password whenever the gateway is unreachable, and its WebSocket on port 81 has no authentication. Upstream lets anyone on that access point turn the E-Stop off, move its pin, change the Wi-Fi networks and link the hub to another account. Softproxy SP-46 (TIN-7125 `fd8d8374`) refuses those commands there. The serial port stays the local path.

`kLocalSocketAllowed` in `include/softproxy/Lockout.h` is an allow list, now empty, checked in `src/message_handlers/websocket/Local.cpp` before dispatch. A refused command is logged (`Refusing local socket command <name>`) and the client gets the error message `refused_local_command`.

| Local command | Upstream 1.5.2 | This fork | Serial path |
| --- | --- | --- | --- |
| `SetEstopEnabledCommand` | allowed | refused | `estop enabled` |
| `SetEstopPinCommand` | allowed | refused | `estop pin` |
| `WifiScanCommand`, `WifiNetworkSaveCommand`, `WifiNetworkForgetCommand`, `WifiNetworkConnectCommand`, `WifiNetworkDisconnectCommand` | allowed | refused | `networks` |
| `AccountLinkCommand`, `AccountUnlinkCommand` | allowed | refused | `authtoken` |
| The nine `OtaUpdate*` commands | empty handlers | refused, so a later upstream body cannot open an install path | none needed |
| `SetRfTxPinCommand` | allowed | refused (SPR-75): the pin could be moved onto the E-Stop GPIO | `rftxpin` |
| a payload a later release adds | handled | refused until it is added to the list | |

The portal itself still serves the static frontend, and the access point still opens while the gateway is down. It no longer opens because the radio failed while the gateway is connected (`kOpenPortalOnRadioFailure`), since the socket has no repair command to offer.

The socket's defragmenter holds one fragmented message to `kLocalSocketMaxMessageBytes` (4096 bytes, the verifier limit) and uses `TinyVec::try_append`, so an endless fragment stream or a failed allocation drops the message and disconnects the client. Upstream appended with no bound until the `TinyVec` panic restarted the hub, before the allow list saw any message. A client can still spend heap in other ways, so the kill path does not depend on the hub never restarting (see Kill path).

## Kill path

The E-Stop is software on the same ESP32 that drives the radio. `include/softproxy/KillPath.h` holds its rules, and `src/EStopManager.cpp` applies them.

| Rule | Behaviour |
| --- | --- |
| Contact (R-SOFTPROXY-ESTOP-NC, SP-174) | The E-Stop is a latching mushroom with a normally closed contact to ground, and the input is pulled up. This amends the normally open contact of SP-136 and SP-166. Closed reads low and means run. Open reads high and means stop: a pressed mushroom, a cut or unplugged cable and an unwired pin all read high. The checker task samples the pin every 5 milliseconds and reads it as a level. A full window is 13 samples, 65 milliseconds |
| Armed | `IsArmed` needs the checker task running on a valid input pin, a sample taken since that task started and a sample in the last 1000 milliseconds. The task keeps a flag for the first sample, so a task that just started, at boot or after `estop pin` moved it, is not armed until it has read the pin (review H5). `HandleCommand` refuses shock and vibrate otherwise (`estop-not-armed`). This covers no pin, a disabled task, a stalled task and a config that fell back to defaults while the caps survived. Stop, Sound and Light still pass when not armed and released. The transmit task reads `IsArmed` on every pass as well: a stalled checker cannot latch a press, so a hub that is not armed ends every shock and every vibrate above intensity 0 already in flight, with its terminator, as an engaged one does (review H2). A pulse admitted before the stall therefore stops about 1000 milliseconds after the last sample instead of at its end. A vibrate at intensity 0 runs its full length, because it is the stop frame that `SendCommand` makes of a Stop, the keep-alive and the terminator. Sound and Light run on too. The checker posts its state event with a 5 millisecond wait, not an endless one, so a full event queue cannot hold it away from the pin. A failed post is tried again on the next pass, and the latch never waits on it. Each failure counts. The first logs at once, and while posts keep failing the log repeats at most every 10 seconds with the count since boot (review T2). The checker also keeps the longest interval between two of its samples since boot, so the bench can read how close the real worst gap comes to the 1000 millisecond window (review T1). The window stays 1000 milliseconds until that reading exists. `estop state` prints both on a plain line before its reply, `softproxy-estop-health maxSampleIntervalMs=<n> failedStatePosts=<n>`, with no `$SYS$` prefix. Softproxy reads the reply line strictly and refuses any extra field, and its read ends at the first `$SYS$` line, so the health line stays off both |
| Engaged | The latch is one retained value, written only through `estopmanager_writelatch`. It records what set it: `cold-boot`, `gateway`, `button` or `unconfirmed` (SP-156). One high sample engages at once, at any time, with source `unconfirmed`. The source turns `button` only for a real edge: the checker task read a full window of low samples, a measured run, and that press then reached a full window of high samples. A pin already high when the task starts, as after `estop pin` onto an unwired pin or a boot with the cable unplugged, engages and stays `unconfirmed`, however long it stays high. Otherwise the first source holds until the clear, so a later press or `Trigger` does not restate it. While engaged every command refuses (`estop-engaged`), including Stop, as upstream does. The transmit task discards what reaches its queue and, on every pass, ends sequences in flight with their 300 millisecond terminator. Leaving the E-Stop restores the stored keep-alive setting, and a failed read leaves keep-alive off |
| Release (SP-174) | Only the clear releases it. The task must first measure the mushroom down, a full window of high samples, while engaged. Then the mushroom is twisted up: once a full window reads low, the clear counts 1000 samples, 5 seconds at 200 Hz, and it releases if every one reads low. It counts samples and not wall time, so a checker that stalls during the clear does not shorten it. Any high sample stops the clear, whether a push, a bounce or a cable fault, and the next full window of low samples starts it again from the beginning. The mushroom down never clears, however long it stays down. SP-174 replaces SP-167's hold-to-clear, and no held-press clear remains |
| Cold boot (SP-158) | `Init` restores the retained record only when `esp_reset_reason()` is `ESP_RST_SW`, `ESP_RST_PANIC`, `ESP_RST_INT_WDT`, `ESP_RST_TASK_WDT` or `ESP_RST_WDT`. This is the warm list. Every other reason, including power-on, brownout, EN and unknown, starts engaged with source `cold-boot`, whatever RTC memory kept, because a kept record passes its check. Every command refuses until the clear, so a power cycle with nobody at the hub leaves every command refused until the operator clears it by hand: push the mushroom down, then twist it up and leave it up. A mushroom already up at the boot does not clear by itself. With no pin stored, nothing can clear it until `estop pin` and `estop enabled true` run. A retained record that fails its check reads the same way |
| Restart (SP-172) | The latch lives in RTC no-init memory, so a reset on the warm list comes back as it was, with the same source, and `Init` restores it before any command can arrive. A hub that was released comes back released, and an engaged hub comes back engaged. **A crash loop never forces a stop:** a released hub that panics or trips a watchdog over and over comes back released each time, and only the mushroom, the cable, the gateway or a cold boot engages it. Starting the task reads the latch and never writes it. A clear under way does not survive a restart: the restarted task measures the mushroom down again before a clear |
| Gateway `Trigger` `EmergencyStop` | Latches at once, with or without a checker task, with source `gateway`. It allows no cap rise. On a hub with no task and no stored pin only a power cycle ends it, and the hub then holds the cold boot latch. With a stored pin `estop enabled true` starts the task, and the clear releases it. While engaged it stops a clear in progress, and the next clear needs the mushroom pushed down and twisted up again. `Trigger` counts each stop before it engages, and the release refuses while a stop the checker task has not taken is pending, so a stop that races the end of a clear never lets `IsEStopped` read false. The hub ignores every other gateway `Trigger` while engaged |
| Serial `estop` | `estop enabled false` and a new `estop pin` refuse while a press, an open contact or the gateway holds the E-Stop engaged or any cap is above 0. The cold boot latch leaves them open with every cap at 0, because a freshly flashed hub starts there and needs its first pin. No setting releases the latch, and that latch never allows a rise. They are also open at released with every cap at 0, where a move onto an unwired or open pin engages as `unconfirmed` and allows no rise. `safetycaps clear` unlocks them on the cold boot latch at once, and otherwise once the E-Stop is released. `estop enabled true` refuses with no valid pin. `estop state` prints the running state and the source, where `estop enabled` and `estop pin` print the stored config |
| Pin separation (SP-113 rule 1) | The E-Stop pin refuses the stored RF TX pin, the board's default RF TX pin, the board LED pins and, on a plain ESP32, GPIO 34 to 39, which have no internal pull-up, so an open contact there could read low, which is run. On a plain ESP32 it also refuses the strapping pins, whatever the board bypasses: GPIO 0 and 2 (boot mode), 12 (flash voltage, and the RF line on `Pishock-2023`), 15 (boot log) and 5. A normally closed contact holds its pin low and an open one leaves it high, so on a strapping pin the button would decide how the hub boots. It refuses GPIO 6 to 11, the flash pins, through the same rule. Both pins also refuse GPIO 10 through `CHIP_UNSAFE_GPIO`, a flash pin upstream's list leaves out. The RF TX pin refuses the stored and running E-Stop pins and the LED pins. The rule reads the pin set at run time, because no `Pishock-*` env defines `OPENSHOCK_ESTOP_PIN` and the two envs differ on RF TX (12 on `Pishock-2023`, 15 on `Pishock-Lite-2021`). `rftxpin`, `estop pin`, `jsonconfig`, `rawconfig`, `SaveFromFlatBuffer` and both `Init` paths all check it. `jsonconfig` and `rawconfig` also set `rf.txPin` and the E-Stop fields, so they obey the same lock as serial `estop` |
| Boot | A stored config that breaks these rules leaves the E-Stop off, which is not armed, so shock and vibrate refuse. A stored RF TX pin on the E-Stop pin or a board LED also leaves the radio off, and `rftxpin` repairs it. The hub still boots, so the serial port stays usable |
| Cap rise (SP-113 rule 2, SP-156) | `SafetyCaps::Set` refuses a write that raises any cap unless the E-Stop is armed and a button press holds it engaged. Armed means a live checker task, and the source must be `button`. A gateway `Trigger`, a cold boot and an `unconfirmed` latch do not count, on an armed hub either, because none shows that a press reaches the pin. A cold boot or an unwired pin reads high from the start, so it gives no button source. A press during a held latch changes no source, so a rise needs a clear and then a press from released. A `button` latch keeps its source through a warm restart, and the settings stay locked, so the pin stays the one that was pressed. `factoryreset` is the exception: it writes the default config with no lock check and the latch survives it. The hub then comes back with a `button` latch and no pin, not armed, so a rise refuses and a power cycle ends it. A lower `minGapSec` and any change of `stageJoinMs` count as rises, since a shorter join window can turn a command refused `over-pulses` into a new stage. Other lowering and `safetycaps clear` need no E-Stop |

Order at the attended session, with every cap at 0, from the cold boot latch, with the mushroom up and the contact wired: `estop pin <n>`, `estop enabled true`, check `estop state` reads `source=cold-boot`, push the mushroom down, twist it up and leave it up for 5 seconds, check `engaged=false`, push the mushroom down past the 65 millisecond window, check `source=button`. If `estop state` still reads `engaged=false` with the mushroom down, the two wires are shorted together or the pin is shorted to ground, the known residual under SP-157: stop there and fix the wiring. Then `safetycaps ...`, then twist it up and leave it up for 5 seconds. That session waits for Softproxy's allow-listed serial driver, and nobody sends `rftransmit` by hand (SP-162). The order leaves two stated residuals open. First, SP-172 keeps `ESP_RST_WDT` on the warm list, so an RTC watchdog reset after a short power blink that kept RTC memory could restore a released latch. That is inferred and unverified, and the power cycle row below checks it by expecting `source=cold-boot`. Second, a solid open of 65 milliseconds or more after a measured run reads as `button`, so an intermittent cable could allow a cap rise. A rise still needs a `safetycaps` write over the serial port.

The same session carries one accepted loss. A stored E-Stop byte of -128 to -2 fails the load at boot, so `Init` writes the defaults over the whole config file. The loss covers Wi-Fi, the backend domain and auth token, the RF TX pin and keep-alive, the OTA settings, serial echo and the captive portal always-on flag. The caps sit in `spcaps`, outside that file, so they stay. It is accepted because an E-Stop with no pin is not armed, so shock and vibrate refuse whatever the caps hold. An app-only write keeps the stock config, so the first boot reads it. A merged write at 0x0 likely erases it (I, esptool not run). Either way the stock backup step runs first where the fork allows (SP-137). A hub that comes up with no E-Stop pin and no stored Wi-Fi may have taken this path. The boot that wiped the file logs `Refusing E-Stop pin`, and later boots do not. With no Wi-Fi it also opens its no-password access point, as on any bench with no gateway. To recover, Jess first runs `safetycaps clear` if any cap is above 0, because `estop pin` refuses while a cap is set (SP-10), then check `rftxpin`, set the Wi-Fi again, pair the backend again only if this hub used it, and start the order from `estop pin <n>`. If `estop pin` is still refused after `safetycaps clear` printed `Cleared caps`, `estop state` shows why. A `button`, `gateway` or `unconfirmed` source keeps the settings locked. Power-cycle the hub so `estop state` reads `source=cold-boot`, which leaves the settings open, then start the order. At `cold-boot` or `released` the refusal comes from the pin itself: the RF TX pin, a board LED, a strapping or flash pin or a pin with no pull-up. If the caps store cannot be read, the settings lock counts the caps as set, so the E-Stop settings stay locked even from a cold boot. `safetycaps` still prints every cap as 0 with `set=false` on both channel lines, as it does for cleared caps, so the readout alone cannot show this. The hub log names it: `Failed to open caps storage`, `Failed to read stored caps` or `Stored caps record has an unknown layout`. Run `safetycaps clear` once. Go on only if it printed `Cleared caps` and, after a power cycle, the log names none of those three lines. Otherwise stop the session there. Do not run the clear again, erase the rest of NVS or reflash to get past it. Record the log lines and what `safetycaps` printed. No board has run this path.

What the firmware cannot see:

- The contact must be normally closed to ground, with the mushroom up. A normally open contact wired by mistake inverts the gesture: the hub stays engaged with the mushroom up and clears 5 seconds after it is pushed down. The attended order shows it at the first clear, where `estop state` reads engaged after the twist up. Stop there and rewire.
- A cut cable reads as a press. After a measured run it records `button`, so a cut cable on an armed hub can allow a cap rise exactly as a press does. Reconnecting the cable with the mushroom up for 5 seconds clears, as a twist up does. The firmware cannot tell a cable fault from the mushroom.
- `source=button` shows a low level for a full 65 millisecond window and then a high level for another, not a hand on the button, so a burst of noise that long reads as a press. A shorter high engages with `source=unconfirmed`, and so does a press in the first 65 milliseconds after the task starts. A pin with nothing wired engages the same way and locks the settings, and because it never gives a clear, a power cycle is the way out: the cold boot latch opens the settings again. An `unconfirmed` latch needs a clear before a press can allow a rise.
- The mushroom that engages also clears. SP-174 keeps the twist up as the only clear, with no second factor.
- The contact closing to ground is the only run level, and any other reading counts as stop. A short between the two wires, or from the pin to ground, reads as run with the mushroom down, and nothing detects it. That is the known residual under SP-157.
- An RTC watchdog reset reads as warm (SP-172). After a short power blink that kept RTC memory, a board that reports `ESP_RST_WDT` could restore a released latch. This is inferred and unverified. The power cycle row expects `source=cold-boot` and is the check.
- A solid open of 65 milliseconds or more after a measured run reads as `button`, as a press does. An intermittent cable could therefore allow a cap rise, but a rise still needs a `safetycaps` write over the serial port.

| X8, count read outside the mux | Same window | Test gap. The product compares inside the critical section | Killed by the same scenario |
| X2, count read before the flag clear | Fails safe: later releases refuse | Test gap | Killed by the same scenario |
| X6, task start takes no stop | Fails safe: a clear costs more | Test gap | Killed by the same scenario |

The host test now runs code at the edges of each outermost latch section, before it or after it, which are the two orders a contended lock allows. One thread is awake at a time, so real-core interleavings and their timing stay unmeasured. The review's X7, X9 and X11 sit in the harness `EQUIVALENT` list, each with its reason.

The review's X10 also survived. It ends the confirm of a press in progress when the checker takes a gateway stop. That fails safe, but it is observable: a press that engaged before the stop then stays `unconfirmed` and refuses a cap rise, where the code confirms it as `button`. `pressThenGatewayStopStillConfirms` pins the code's result, and X10 is a harness mutant that goes red in it.

`EStopConfig::FromFlatbuffers` takes the stored pin as a signed byte. `GPIO_IS_VALID_GPIO` in arduino-esp32 2.0.17, the core behind `framework-arduinoespressif32 ~3.20017.0` in `espressif32 @ 6.12.0`, is `((1ULL << (gpio_num)) & SOC_GPIO_VALID_GPIO_MASK) != 0` with no sign check, so a negative pin other than -1 reaches an undefined shift. The parser now refuses those bytes and leaves -1 as no pin.

A refusal fails `SaveFromFlatBuffer` and `SetRaw`. At boot it fails the load of a stored config, so `Init` writes the defaults over the whole file, Wi-Fi included, and on both PiShock envs the E-Stop comes up with no pin and not armed. The JSON path reads the pin as an unsigned byte, so a negative number there falls back to the build default and never reaches the macro. The port 81 `SetEstopPinCommand` and `SetRfTxPinCommand` also pass a signed byte to the same check. `LocalSocketAllows` refuses both before they run, so this change leaves them. A byte past the last pin still parses, keeps its number and reads as not enabled.

`negativeEStopPinsAreRefused` and `realLeafParsersRun` hold these results. CI builds that test with the shift sanitizer, which traps if a negative pin reaches the macro. P1 to P9, M1, M23 and M24 are the harness mutants. M1 pins the top of the guard: a stored pin 0 still loads and reads as not enabled. M23 and M24 pin the JSON range check: -243 and 269 fall back to the default, and each would wrap to pin 13 as a byte.

The CADE-1 review of `25f1449` found these gaps. No run-time product code changed for them. F4 adds a compile-time check and a build define:

| F1 | Removing the pin rule from `SetEStopEnabled` survived | `enableRefusesAStoredConflictingPin` boots on a stored pin the rule refuses, then runs `estop enabled true`. Mutant X12 goes red |
| F2 | The three whole-config writers had only a text scan | `test_config_writers` links the real `Config.cpp` and `RootConfig.cpp`. Each writer is refused under every lock and on each pin clash, and writes nothing then. Mutants C1 to C3 and K49 go red there |

## Refusal report

Before this change a refused step left one log line and nothing else, so Softproxy logged an actuation that never reached the shocker (softproxy #27 review, finding 4). `SafetyCaps::Admit` now counts every cap refusal in `include/softproxy/RefusalReport.h` and writes one log line, and `HandleCommand` does the same for the E-Stop refusals through `SafetyCaps::RecordRefusal`. Serial `rftransmit` commands pass there, and so do the gateway commands the lockout lets through, Stop and Sound. A Stop, Sound or Light refused by an engaged E-Stop logs `channel=other`.

| Trace | Form | Read by |
| --- | --- | --- |
| Hub log (serial) | `softproxy-refusal seq=<n> channel=<shock\|vibrate\|other> verdict=<name>`, level warning, kept by the production log level `INFO` | Softproxy on the local serial path |
| Gateway heartbeat | `Pong.softproxy_cap_refusals` (`uint32`, field 2, vtable offset 8): refusals since boot, saturating at 16777215. `Pong.softproxy_last_refusal` (`uint8`, field 3, vtable offset 10): verdict code of the latest refusal. `Pong.softproxy_estop` (`uint8`, field 4, vtable offset 12): bit 0 armed, bit 1 engaged | the gateway, on every Ping |
| Serial `safetycaps` | `SafetyCaps\|refusals\|count=<n>,last=<name>` and `SafetyCaps\|estop\|armed=<bool>,engaged=<bool>,source=<released\|cold-boot\|gateway\|button\|unconfirmed>` after the two channel lines | the operator or Softproxy |
| Hub log on an E-Stop change | `softproxy-estop state=<idle\|active\|active-clearing>`, level warning. `active-clearing` is the 5 second clear. The name `awaiting-release` belonged to SP-167's hold-to-clear, and nothing logs it since SP-174 | Softproxy on the local serial path |

The verdict names are those in the cap table above, plus `caps-not-set`, `boot-hold`, `estop-engaged` and `estop-not-armed`. Wire codes: 0 none, 2 `caps-not-set`, 3 `boot-hold`, 4 `over-intensity`, 5 `over-pulse-ms`, 6 `over-pulses`, 7 `gap`, 8 `hourly`, 9 `daily`, 10 `estop-engaged`, 11 `estop-not-armed`, 12 `over-on-time`. A receiver that sees `softproxy_cap_refusals` rise between two heartbeats knows that many steps were refused. The count lives in RAM and restarts at 0 after any reboot, which a lower `uptime` in the same `Pong` shows.

The three fields come after `uptime` and `rssi`, so a gateway built from the upstream schema reads the heartbeat as before and ignores them. `softproxy/schemas/HubToGatewayMessage.fbs` holds the fork schema. The `schemas` submodule still points at upstream commit `aaceae18`. `include/serialization/_fbs/HubToGatewayMessage_generated.h` is byte-identical to the output of `scripts/flatc` (version 25.9.23) for that fork schema, laid over the submodule, with the C++ flags in `scripts/generate_schemas.py`. `scripts/generate_schemas.py` itself reads only the submodule, so running it unchanged would drop the three fields.

## Who can set the caps

The caps live in their own NVS namespace (`spcaps`), outside the config file. `rawconfig`, `jsonconfig`, the captive portal and the gateway cannot read or change them, and with OTA installs refused the gateway cannot replace the code that reads them. Only the local serial port can:

| Serial command | Effect |
| --- | --- |
| `safetycaps` | print both channels, whether each is set and the stages counted since boot |
| `safetycaps shock <maxIntensityPct> <maxPulseMs> <maxPulsesPerStage> <minGapSec> <maxPerHour> <maxPerDay> [stageJoinMs]` | store the shock caps |
| `safetycaps vibrate ...` | store the vibrate caps, same arguments |
| `safetycaps clear` | set every cap to 0 |

Raising a cap needs the E-Stop armed and engaged by its button (see Kill path). `factoryreset` also clears the caps. The operator sets the values at an attended calibration session (Softproxy SP-10). The real values live only in the Softproxy private registry and never in this repository. Softproxy's alarm service must never send `safetycaps shock` or `safetycaps vibrate`. It may read `safetycaps` and refuse when the hub caps differ from the registry.

## Not covered here

- The hub cannot see a request's purpose, schedule or arm state. Those stay Softproxy server checks 4 to 8.
- The output bound is per channel. Shock and vibrate each hold one run, so a sender that alternates them on one shocker can keep that shocker's output on longer than either bound, with the electrical part still bounded by the shock run. Two receivers on one channel each stay within the bound, and their sum is twice the counted time (review N4).
- The bound limits unbroken output, not the duty cycle or the dose (review N1). It allows a run of one full stage, then 300 milliseconds off, then another. In the review's model of the RF task, caps `maxPulseMs` 2000, `minGapSec` 2, `maxPulsesPerStage` 1 and `maxPerHour` 1800 kept a shocker on for 87.0 percent of an hour in 2000 ms runs with 300 ms breaks (M in the model, at the commit before review N2). Counting the frame lengthens each break by one frame, and the same model with a sender that retries every millisecond still reaches 85.3 percent with the review's 45 ms frame (M in the model). The hub has no hourly on-time cap. Output per hour is bounded only by `maxPerHour * N * (P + 73)` on the air. Whether the hub should bound dose waits on Jess's ruling (review N1). Until then the duty cycle stays with the gap, the hourly and daily caps and Softproxy's server checks.
- Hourly and daily counters do not survive a power cycle. The cold boot hold spaces stages after one, and the server counters stay the authority (see Fail closed).
- RTC no-init retention across a software, panic and watchdog reset is ESP-IDF behaviour, not yet checked on the PiShock boards. Many boards reach EN from the serial adapter's DTR and RTS, so opening the serial port may reset the hub, and SP-112 makes serial the calibration path. The reset reason each board reports for that is unknown. See the serial-port reset row under Kill path. This is general ESP32 knowledge, unchecked on these boards.
- The upstream live control gateway (`openshock/live-control-gateway:3.17.0`) does not read the three `Pong` fields. They reach it on the wire, but Softproxy sees them only through a gateway change or by reading the serial log and `safetycaps`.
- The refusal count restarts after every reboot. A refusal just before a reboot shows in the hub log, not in the next heartbeat.
- The TypeScript code generated for the frontend (`frontend/src/lib/_fbs`) still has the upstream `Pong`. The frontend never reads it.
- No `Pishock-*` board environment defines `OPENSHOCK_ESTOP_PIN`, so the E-Stop starts with no pin, not armed, until `estop pin` and `estop enabled` run over serial. Until then and until the clear, every command refuses.
- RTC no-init retention of the E-Stop latch and the `esp_reset_reason()` value on each reset are the same unverified ESP-IDF behaviour as the counters above. The host test fakes the reset reason and keeps the sealed record across each reason, so a cold boot on a kept record is tested on the host only.
- The E-Stop rules are host-tested with a fake GPIO. It reads an undriven pin high with the pull-up and low without it. A switch, a cable, a cable pull and the board are tests for the attended session.
- The host test's fake `Chipset` accepts pins 0 to 39, so `CHIP_UNSAFE_GPIO`, the `OPENSHOCK_BYPASSED_GPIO` entries and the `int8_t` signature of the real functions do not run there. A scan pins GPIO 10 in the real ESP32 list. The E-Stop's own refusal of the strapping and flash pins lives in `KillPath.h`, so it runs on the host for both PiShock RF TX builds and holds whatever a board bypasses. GPIO 12 and 15 are refused as E-Stop pins on both envs. `rftxpin` still follows the board's bypass list, and the hub revision read covers which env is right.
- The cold boot latch publishes no state event while no checker task runs, so the LED shows it only after `estop enabled true`. `estop state`, `safetycaps` and the `Pong` field show it from boot.
- The keep-alive frames are read, not run. The host test starts and stops the keep-alive task on the E-Stop state event, but sends no keep-alive frame.
- The whole-config writers run on a fake LittleFS and a small fake cJSON. Their RF and E-Stop parsers are the real ones and the other leaves parse nothing, so the real cJSON, the filesystem and the other leaf configs do not run on the host. The GPIO macros in that fake are a copy of the ESP32 definitions in arduino-esp32 2.0.17, so a change of framework needs a fresh read of them.
- A serial `rftransmit` command in the host test comes from a fake parser, so `JsonSerial::ParseShockerCommand` is read, not run.
- Stack margin on `main_app` for the refusal path is not profiled. `SealRetained` and `RestoreRetained` no longer put the 2 kilobyte record on the stack. The path still runs `snprintf` and a log call on each refusal.
- Caps live in NVS, so a re-flash with no erase keeps them. After a clear they admit commands with no press on that boot, and the cold boot latch cannot show that they are stale. Reading `safetycaps` after a flash is the only guard.
- Once the clear has released the cold boot latch, the image can transmit at every cap 0. Stop becomes a vibrate frame at intensity 0, as do the keep-alive and every terminator, and Sound is uncapped up to 65535 milliseconds. The encoding is non-electrical by source reading only. What a receiver does with a vibrate frame at intensity 0 is unmeasured.
